# ADR-0030: AI assistance (Phase 10)
Status: Proposed. Builds on [ADR-0010](0010-work-orders-and-requests.md) and [ADR-0024](0024-hardening.md).

## Decisions
- **Optional, off by default, and the operator decides whether it can exist at all.** Two switches. The *operator* of the installation sets a provider in configuration (`Ai:Provider`, `Ai:ApiKey`, `Ai:Endpoint`, `Ai:Model`); with none set, AI is not available and the app says so. The key lives in server configuration or the key vault: it is never stored in the database and never sent to the browser. The *organisation's administrator* then turns AI on (`ai.manage`), chooses which suggestions are offered, and sets a daily limit. An on-premise customer who forbids AI simply leaves the provider unset; nothing is sent anywhere.
- **A provider interface.** `IAiProvider` takes a system text and a user text and returns text and token counts. The first provider speaks the Claude Messages API with `HttpClient` (no new package); `Ai:Endpoint` can point at a gateway or private endpoint. The key is sent only to an `https` address (or a loopback address, for tests). A fake provider stands in for tests. Errors are returned as short results; the service's response body and the words exchanged are never logged.
- **Suggestions only.** The AI never changes a record. A suggestion is shown to the person with "written by AI, check it", and a button to use it or dismiss it. Two suggestions exist: a **category and priority for a request being written**, and a **short summary of a work order**.
- **What is sent is cleaned and minimal.** Only the words of the one request or work order being looked at (title, details, place, asset, status, the history notes and comments) and the organisation's category names. E-mail addresses, web addresses and long numbers are replaced before sending; control characters are dropped; each text is cut to a length. No names of people, no attachments, no other records, no other organisation's data. The system text tells the model the request is untrusted data and its instructions must not be followed.
- **What comes back is checked.** The triage answer is read as JSON and only a category code the organisation really has and one of the four priorities are accepted; an invented value is dropped. A summary is turned into plain text (markup characters removed) and cut. A reply with nothing usable is reported as such. The web app shows everything as text, never as markup.
- **Limits protect the bill and the people.** A daily limit per organisation (0 to 5000, default 200), 30 suggestions per person per hour, a short output cap and a timeout. Once a limit is reached no call is made.
- **Use is recorded without the words.** An append-only usage log (application and database trigger) holds when, who, which suggestion, answered or failed, token counts and the work order concerned. There is nowhere in it to keep text. Switching AI on or off or changing the limit is audited with before and after. Administrators see use for 30 days.
- **No training.** The product does not use an organisation's data to train or fine-tune anything. Whether the provider keeps or trains on API traffic is the provider's contract with the operator; the operator should check it.
- **Maintenance hints without a model.** "Assets with repeat problems" lists assets with three or more repair requests in 90 days (both numbers adjustable), by counting work orders. It does not use AI, so it works whatever the switches say, and it shows its reason (the count).

## Consequences
- No feedback loop yet (accept or ignore is not recorded), so the quality of suggestions cannot be measured from the product.
- Arabic requests are sent as written; quality depends on the model. Prompts and category names are in the organisation's own words.
- Suggestions are not offered on the technician mobile app or offline.
- The hourly and daily counters are database counts, so they hold across several servers, but a burst can slightly overshoot a limit.
- Natural next steps, not built: recording accepted or ignored suggestions, a suggested assignee or vendor, duplicate-request detection, predictive maintenance from meter data.
