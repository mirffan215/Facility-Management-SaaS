# ADR-0015: Inventory (Phase 4)
Status: Proposed. Builds on [ADR-0010](0010-work-orders-and-requests.md), [ADR-0012](0012-work-order-evidence.md) and [ADR-0014](0014-preventive-maintenance.md).

## Decisions
- **Its own module** (`Fms.Inventory`, schema `inventory`, own migrations), unlike preventive maintenance, because stock is a separate subject with its own people and rules. Row-level security on every table; the movement ledger is append-only in code and by a database trigger.
- **Modules talk through contracts in BuildingBlocks**, never across schemas. Inventory asks the Work module (`IWorkOrderLookup`) whether a work order exists and still takes parts, and whether a PM template exists. The Work module asks Inventory (`IWorkPartsLookup`, optional) for the cost of parts issued, and calls `IPmPartsReserver` (optional, best effort) after it creates a preventive work order. Without Inventory registered, both are simply absent.
- **Reserve, then issue** (the customer's decision). A reservation holds stock for a work order: `Reserved` goes up, `OnHand` does not. *Available = on hand − reserved.* Issuing takes stock out at the store's average cost, first using the work order's own hold; it can never use stock held for another work order. Unused parts come back as a return at the cost they left at. Reservations are released when the work order is cancelled, verified or closed (a message from Work, handled by Inventory, safe to repeat) or by hand.
- **Weighted-average cost** (the customer's decision), per store and item. Every receipt, return or transfer-in re-averages; issues and transfers-out leave the average alone; transfers carry the source's cost. No cost layers, so no FIFO reports; revaluation is not supported.
- **Parts cost lives in one place.** Issues are movements tagged with the work order. The work order's *material* cost is the sum of those movements, net of returns, added to any material lines typed in by hand. There is no copy into the Work tables, so the two cannot disagree and there is no two-database write.
- **The ledger is truth.** `StockMovement` rows (signed quantity, unit cost, balance after, who, when, work order / transfer / stock take, reason) are never edited. A `StockLevel` row per store and item keeps the running figures for speed, guarded by a row version and database check constraints (`OnHand ≥ 0`, `Reserved ≥ 0`, `Reserved ≤ OnHand`). Concurrent changes retry from a clean read; a test proves ten simultaneous issues against five units issue exactly five.
- **Stock takes with a second person.** Counting freezes the system quantities per line. Submitting needs every line counted. Approval, by someone with `inventory.approve` **other than the submitter**, posts the *differences* (counted − frozen) as count-adjustment movements, so stock received or used during the count is kept. An approval that would cut into stock held for work orders is refused with the item named; the count can be sent back. Direct adjustments outside a stock take need `inventory.approve` and a reason.
- **Reorder.** Optional minimum and maximum per item and store. *Low* means available ≤ minimum. Crossing into low sends one notice to people with `inventory.manage` (outbox, in-app and bilingual email) and sets a flag that clears when stock recovers, so a dip notifies once. The low-stock list suggests an order quantity (up to the maximum, or twice the minimum). No purchase order is created: that is Phase 5.
- **Preventive maintenance parts.** A template carries a parts list (kept in Inventory, keyed by the template's id). When a visit's work order is created the parts are reserved (the template's store, else the work order's site, else the store with most available). A line that cannot be fully met is skipped, never half-reserved, and the shortage is audited (`inventory.reservation_short`); the visit is always created.
- **Permissions.** `inventory.read` (managers, technicians, viewers), `inventory.manage` (items, stores, receive, transfer, reserve, reorder levels, count), `inventory.issue` (managers, technicians: issue and return), `inventory.approve` (managers: approve counts, direct adjustments).

## Consequences
- One currency per tenant is assumed (the Work settings currency); unit costs are numbers without a currency code.
- Reservations are per work order, store and item. A work order cannot reserve the same item from two stores in one step.
- Receiving has no purchase-order link yet; the reference field takes a delivery-note or invoice number.
- Serial and batch tracking, expiry dates, bins within a store and units of measure conversion are not modelled.
